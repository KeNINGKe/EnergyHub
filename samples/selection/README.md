# 精选价值标注（内容质量升级方案 C-01）

> 目的：给「每日精选 12 条」的评选标准建立人工标注基准。
> 数据与基线同源：samples/daily/ 的 7 个基线日（2026-07-30 ~ 08-05，
> 与旧相关性标注集同一批快照）。标注与 A/B 阶段开发并行进行。

## 文件

- `set.json`：180 条待标注样本（固定种子 20260929，可复现）。
  分层：旧标注「相关」77 条全留（精选判定核心）＋「无关」35 条全留（噪声层）＋未标注随机补 68 条。
- `labels.json`：人工标注结果。当前 0/180。
- `review.html`：标注页面，双击打开，无需服务器。

生成/重生成：`npm run annotate:selection`。重新生成**不会**覆盖已填标签。

## 标注字段

| 字段 | 取值 | 说明 |
|---|---|---|
| `decision` | `select` / `reject` / `either` | 假设每天只能给读者看 12 条消息，这条值不值得占一个位置。`either` = 两可，不计入准确率分母，拿不准就标它，别勉强 |
| `isMajorEvent` | `true` / `false` / `null` | 当天储能/AIDC 圈的大事件（大额订单、重大政策、头部厂商大动作）。留出集中已标 `true` 的事件若被漏选，评测单独计数 |
| `eventGroupId` | 组号字符串 | 两条是**同一事件**时填同一组号。预填的 `eg` 编号来自旧标注的重复关系，可直接沿用或改。评测划分开发集/留出集时按事件组分，同一事件不得跨集合 |
| `reason` | 字符串 | 标注理由，一两句即可。尤其 select/reject 边缘案例请写清楚为什么 |
| `confidence` | `high` / `medium` / `low` | 对本次判断的把握 |

`preAnnotation`（在 set.json 里，非标注结果）：旧相关性标注的线索——
「旧:无关」「建议 reject」徽标大概率是 reject；「旧:低质量」是相关但软文/信息量低的条目。
**线索只是线索**：旧标注判的是「相不相关」，本次判的是「值不值得进精选」，两个问题不一样。

## 判定标准（业务语言）

select 的正向理由（符合任一即值得考虑，越核心越该 select）：

1. **对业务有直接信息量**：具体项目（地点/容量/金额/时间）、具体政策（谁、管什么、何时生效）、具体技术或产品进展——看完能回答「所以呢？」。
2. **影响供需或格局**：头部厂商/业主的大额订单、扩产、退出；改变成本曲线的技术；影响北美/中国/中东重点市场的政策。
3. **事实增量**：报道给出新数字、新时间点、新当事方，而不是复述上周已知的事。

reject 的负向理由（符合任一基本 reject）：

1. 软文、通稿模板、展会营销、招聘、融资套话（无具体用途与规模）。
2. 泛泛而谈的观点/预测文（无新事实支撑）。
3. 消费级产品评测、股价变动、与电力/储能/AIDC 供电无实质关联。
4. 同一事件的第 N 篇重复报道（标 reject 并写清 `eventGroupId` 指向主报道那组）。

边界提醒：**相关 ≠ 该精选**。一条消息可以是相关的、真实的、写得不错的，但对读者没有信息增量——reject。
反向也成立：短期看似平淡但给出关键节点（认证、交付、投运）的条目值得 select。

## 标注流程

1. `npm run annotate:selection` 生成/刷新页面（已填标签保留）。
2. 双击 `review.html`；用「只看建议 reject」过滤器先快速过掉明显噪声，再从 q0001 顺序标。
3. 每条：决定 → 重要事件 → 事件组（发现同事件时补齐）→ 理由。
4. 点「导出标注 JSON」，用导出文件覆盖 `samples/selection/labels.json`（或复制粘贴）。
5. 提交时连同 `set.json` 一起入库。

## 标注完成之后（C-01 后续，另行实施）

- 按事件组 70%/30% 划分开发集/留出集，同一事件的转载/中英文版本不得跨集合；
- `scripts/eval-selection.mjs` 输出查准/查全、Top-5 认可率、重要事件漏选数；
- 达到方案 §C-01 冻结门槛后新评分才从影子转正式。
