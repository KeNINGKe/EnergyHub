## 实施中暴露并修复的问题（2026-10-12）

1. **备胎端点双 `/v1`（8a7fbe0）**：`JEV_FALLBACK_BASE_URL` 设为 OpenRouter 惯例的 `.../api/v1` 后代码再拼 `/v1/chat/completions` 得 `/api/v1/v1/…` 静默 404。三轮录制 ~70% 回执全 404 皆此因；排查中被「同 payload 独立重发成功」误导绕了弯路（独立脚本硬编码了正确 URL），最终靠 `JEV_DUMP_FAILED` 落盘字节级请求体定位。`fallbackEndpoint` 归一化剥尾 `/v1`，两种写法兼容，附回归测试。
2. **mergeV2=false 回退路径崩溃（f12f5ac）**：两跑对比首轮直接 TypeError——`mergeEventsLegacy` 无 `grayPairs`，processItems 解构后 `.length` 抛错，配置级回滚开关形同虚设。空数组兜底修复。
3. **备胎瞬时错误重试（2693aac）**：上游 404/408/429/5xx 短退避重试 2 次，成功不记 error，避免夹具被抖动污染。
4. **录制模式增量语义（83d8bc0）**：`--record` 重跑从「全量重调上千条」改为「已有成功回执复用、只补缺失/失败」——清扫残余 error 不再把好回执重新掷骰子（`JEV_RECORD_REUSE=off` 回旧行为）。
5. 陈旧 error 孤儿条目：URL bug 期全调用失败 → topic 仲裁失败 → 下游聚类不同 → 产生如今已不存在的灰区 payload，其 error 条目残留在夹具里污染计数。已手工剥离（回放永不命中，无害；剥离后 `baseline:upgrade` 硬失败兜底确认无真实缺失）。
6. Windows 文件锁（EPERM/EBUSY）依旧高发，既有退避重试机制扛住了。
